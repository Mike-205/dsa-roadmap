# Pass 4: Curriculum Build

Goal (per `00-philosophy.md`): sequence Pass 2's 42-node conceptual dependency graph into an actual learner pathway — milestones, implementation tasks, experiments, readings, review mechanisms — using Pass 3's resource assignments as the material backbone, and explicitly resolving (not papering over) Pass 3's flagged gaps.

## Method

Every milestone below is checked mechanically, the same way Pass 3 checked its heading coverage. `scripts/verify_sequencing.py` parses `02-dependency-graph.md`'s actual `### ` node headings and their `**requires:**` lines directly from the file (not a hand-transcribed copy), parses this file's `## M<n>` milestone headings and their `**Nodes:**` lines the same way, and asserts two things: all 42 nodes are placed in exactly one milestone, and every node-level requirement resolves at the same milestone or an earlier one. Exemplar-level extra requirements (all 13 checked: dynamic array's Amortized cost; chaining's and open addressing's respective backing representations; the heap exemplar's heap property + Contiguity; the unsorted/sorted array Priority Queue exemplars' Sequential representation; Kruskal's Disjoint-set; hash-keyed memoization's Hashing; both Sequence ADT exemplars' backing representations; merge sort/quicksort's Ordering relation; and adjacency matrix/list's Contiguity/Indirection) are stated in 02 as free-form prose under `**exemplars:**` rather than in a machine-parseable field, so these are hand-transcribed into the script (`EXEMPLAR_EXTRAS`), each keyed by the parent node it was transcribed from so a reviewer can spot-check it against that node's line in 02 — documented there as the one part of the check that isn't fully automatic, rather than silently claimed as parsed. Run it with `python3 scripts/verify_sequencing.py`; it exits non-zero and lists every violation if anything doesn't check out. This is a stricter topological sort than "roughly early-to-late": a milestone earns its place only when every one of its nodes' prerequisites has already been taught. The script caught one real error while drafting (below) and passes clean after the fix and after every edit made in response to review below.

**The one error the script caught:** an early draft placed the `Sequence ADT` node itself at the milestone where stack/queue are first introduced (concrete, array-backed only), because that's where the *behavior* first appears. But `Sequence ADT`'s linked-backed exemplar requires `Linked (indirect) representation`, which isn't taught until three milestones later. Fix: split the behavior from the node. Stack/queue are taught concretely and array-only in M3 (no new Pass-2 node is introduced there — it's a pure intuition-building milestone). The `Sequence ADT` node itself — the formal "one interface, two backings" statement — is placed at M5, once linked lists exist, immediately retrofitting the same interface onto the new backing. This is deliberately CS 61B's order (concrete implementations first, interface retrofitted after — confirmed in Pass 3/1b as a second valid sequencing), not Barker's or ODS's (interface-first). Named here because Pass 3 explicitly left this choice to Pass 4.

## Named sequencing decisions

Pass 2's dependency graph under-constrains the order — several valid topological sorts exist. Where this curriculum picked one, here's the reasoning, so a future pass can revisit deliberately rather than by drift:

1. **Trees before graphs**, even though Pass 2 kept "a tree is a constrained graph" as a cross-link, not a `requires:` edge. Pedagogical convenience wins here: hierarchical structure is a strictly easier special case, and every surveyed source (Barker, ODS, CS 61B) teaches it first.
2. **Union-find (Disjoint-set) is taught early — right after linked structures (M6), not grouped with the other tree/hierarchy content in M10.** Pass 2 filed it under "Layer 6 — Hierarchical Structures" by document position, but its actual `requires:` edges are only `Self-referential structure` + `Operation cost as a function of representation` — both satisfied as early as M5. The README calls Princeton's quick-find → quick-union → weighted+path-compressed progression "the README's own canonical friction narrative for the whole curriculum" (Pass 3's own words). Burying that this late wastes it. Teaching it right after linked structures makes it the curriculum's first fully worked example of the friction-driven pattern in miniature — three full iterations, each fixing a named cost problem in the last, before the learner hits anything else that big. It also isn't a tree in the BST/heap sense at all (it's a forest of parent-pointers with path compression), so nothing is lost by decoupling it from Layer 6.
3. **Greedy is taught before finishing graphs**, not after. Pass 2's own edge — `Shortest paths / MST` requires `Greedy paradigm` — forces this: Dijkstra/Prim/Kruskal cannot be taught as instances of a paradigm the learner hasn't seen yet. So Graphs is split into two passes: M11 (representation + traversal — no paradigm dependency) and M13 (weighted graphs + shortest paths — after M12 has taught Greedy). MIT 6.006's own lecture order would pull the other way (it has no standalone greedy lecture at all, per Pass 3), which is exactly why this curriculum isn't just "follow 6.006's calendar."
4. **Red-black trees get the "simplify an existing structure" narrative, not the friction template.** Pass 1b confirmed Bayer's 1972 motivation was simplifying the 2-3-4 tree, not fixing a limitation of an unbalanced BST the way AVL was. Forcing every node into "here's what broke" would be dishonest to this one's actual history — flagged explicitly at M10 rather than smoothed over.
5. **The contiguous/indirect fork is called back explicitly at its 4th occurrence (graph representation, M11) but left as a silent reflection prompt at its 5th (memoization's cache choice, M14).** Per Pass 3's own instruction to call back the pattern, and Pass 2's flag that whether a learner independently recognizes a late occurrence as "the same fork" is a candidate Pass-5 stress-test question. Answering it for them at M14 would destroy the test.
6. **No per-node external problem sets.** Pass 3 was explicit that AoC/Kattis/Project Euler are cross-cutting, Pass-5 practice material, introduced late, not assigned per concept — inventing a per-node problem list here would recreate exactly the merged-checklist approach `00-philosophy.md` rejects. Each milestone below gets one scaffolded friction problem (small, purpose-built to motivate that milestone's idea) and one implementation task — that's it until Pass 5.
7. **Any experiment comparing array vs. linked/indirect representation in Java pairs CS:APP Ch. 6 with the JVM-boxing/Project Valhalla explainer** (`int[]` vs. `Integer[]`/`ArrayList<Integer>`) — flagged once here (per Pass 3), applied at M1, M2, M5, and M9 below without repeating the justification each time.

## Cross-cutting mechanisms

- **Review cadence.** Four checkpoints, placed at natural quarter-points: after M3 (substrate through concrete stack/queue), after M8 (through sorting), after M11 (through graph traversal), after M15 (end of curriculum). Each pairs a short retrieval problem set (pulling from any milestone up to and including that checkpoint, cumulative, not just the immediately preceding block) with **one authored integrative project** — deliberately worded without naming any data structure or algorithm, so choosing a representation is itself part of the exercise, not something the prompt gives away. This is where projects live in this curriculum: not per-node (Pass 3's own rule against that), but at these four checkpoints, each drawing on everything taught so far. The learner-facing prompts are written out in full at each checkpoint below; each project's intended solution and what it's testing for are kept separate, in a "Checkpoint answer keys" section near the end, so the prompts themselves don't give away the representation choice they're meant to test.
- **The 1b learning-science condition, made checkable.** Kapur/Schwartz-Bransford/Kirschner-Sweller-Clark's shared condition (Pass 1b) was: struggle must be a scaffolded, well-designed problem, followed by explicit formalization — unstructured struggle alone doesn't work. Every milestone below is written with two separate, labeled fields so this is auditable per-milestone rather than asserted once and forgotten: **Friction problem** (the scaffolded struggle) and **Formalization** (what gets explicitly named/proved right after).
- **Attempt before instruction (added Pass 5).** The fields above each milestone's Friction problem (Intuition/Formal/Problem) are reference material, not a required reading order — attempt the Friction problem first, using only what prior milestones have built, before reading the Intuition/Formal/Problem fields listed above it in that same milestone. This mirrors the gate Checkpoint 2's answer key already uses explicitly ("read Pearls Col. 1 itself only after attempting this") and is stated once here rather than repeated at all 16 milestones. Without this rule, several milestones' Formal/Intuition fields state the technique the Friction problem was meant to motivate discovering — see `05-stress-test.md` Finding 2.
- **Java experiment pairing.** Per named decision #7 above.
- **Write-before-reading discipline, for CP3 and CP4(b) specifically (added Pass 5, Recommendation 2).** These two are this curriculum's actual transfer-test instruments (see the designer note preceding the answer keys, below) — for them, and only them, write down a complete answer and its reasoning *before* re-reading any earlier milestone or the answer key. This doesn't remove the fact the same person designed the questions, but it does test whether the reasoning is retrievable and applicable under the encoding it was taught, rather than reconstructable with the source material open.

## M0 — Substrate

**Nodes:** Memory as an addressable array

**Why now:** the root node; nothing else has meaning without it.

- **Intuition:** Barker — the video's entire method opens from "it's all one array" (confirmed, Pass 1/3).
- **Formal/substrate:** CS:APP Ch. 6 — storage hierarchy with real latency numbers (confirmed, Pass 3).
- **Friction problem:** none — this is the given, not a derived result (per Pass 2's own facet note: "closer to a given than a derived result").
- **Formalization:** name the two primitive operations (read-at-index, write-at-index) and nothing else; everything built afterward is a strategy layered on top of exactly these two.
- **Implementation task:** none yet.
- **Experiment:** read CS:APP's latency numbers (register → L1 → L2 → RAM → disk) and reproduce the order-of-magnitude gaps with a trivial benchmark (sum an array sequentially vs. via random-order lookups reading the same total data) — first taste of "layout affects cost," before that idea is even named.

## M1 — Representation Primitives & Cost

**Nodes:** Contiguity, Indirection, Operation cost as a function of representation, Abstract Data Type

**Why now:** `Operation cost as a function of representation` requires *both* Contiguity and Indirection to be "in view" (Pass 2's own note: needs at least two representations to be motivated at all) — so Indirection is introduced here as a bare concept (an address stored instead of a value), not yet built into a full linked structure. `Abstract Data Type` then requires cost-as-function-of-representation, which is now available.

- **Intuition:** Barker (core intuition, confirmed thesis) for both Contiguity and Indirection; his own remark that "a pointer is just an index into the array of memory the heap allocator manages" is the bridge that keeps Indirection from feeling like a different mechanism.
- **Formal:** MIT 6.006 (Word-RAM model + asymptotic notation, L1, confirmed taught before the first data structure) — primary; Princeton 1.4 Analysis of Algorithms (placed right before Union-Find) — secondary. ODS/6.006 (confirmed, Pass 3) for the ADT framing.
- **Friction problem:** given two ways to store the same five numbers — packed contiguously vs. as a chain of (value, next-address) pairs scattered in memory — predict, before measuring, which is faster to (a) read element 3, (b) insert a new element between positions 1 and 2. Most learners predict indexed access is "just as fast" for a chain; measuring it is the point.
- **Formalization:** Big-O/Θ/Ω, introduced as the vocabulary for stating the answer just measured — motivated, not dropped in cold. Then the ADT/implementation split: name what changed (the implementation) vs. what didn't (the interface, if any is even stated yet).
- **Implementation task:** implement `read(i)`/`write(i, v)` over a raw array, and a second version over a hand-built chain of boxed `(value, nextAddress)` records; time both for indexed read and positional insert.
- **Experiment:** CS:APP Ch. 6 + JVM-boxing/Valhalla explainer — pairing #1 (named decision 7). This is the first place `ArrayList<Integer>` vs. a primitive `int[]` visibly diverges from Barker's C-level intuition, and it's worth hitting that surprise early rather than letting it silently confuse the Java exercises later.

## M2 — Sequential Representation & Amortized Cost

**Nodes:** Sequential (contiguous) representation (exemplars: fixed array, dynamic array), Amortized cost

**Why now:** requires Contiguity + Abstract Data Type (M1). Dynamic array additionally requires Amortized cost, taught in the same milestone.

- **Intuition:** Barker (array → array-list step of his chain, confirmed) for the friction; MIT 6.006 L2 (confirmed) for the "doubling" argument specifically — **not Barker**, whose chain has no resizing/amortized-cost treatment at all (explicit gap, Pass 1/3, don't misattribute this to him).
- **Implementation:** ODS Ch. 2 (Array-Based Lists, Java) — primary; CS 61B's `AList` — secondary (confirmed, Pass 3).
- **Formal:** MIT 6.042 recurrences — capable of deriving the actual amortized bound (confirmed, Pass 3).
- **Friction problem:** implement a fixed-capacity array list; append past capacity until it throws/overflows. Then: what's the actual cost of "never running out," accounting for the fact that growing means copying everything?
- **Formalization:** the doubling argument and amortized analysis (charge each element a constant amount toward its own eventual copy) — the first real proof-style argument in the curriculum, deliberately motivated by a bug the learner just caused.
- **Implementation task:** implement doubling resize; instrument it to count total element-copies across N appends and confirm it's O(N), not O(N²).
- **Experiment:** CS:APP + JVM-boxing pairing #2 — benchmark `int[]`-backed doubling vs. `ArrayList<Integer>` growth in Java; the boxing overhead should show up as a constant-factor gap, not an asymptotic one — worth confirming that distinction explicitly.

## M3 — Stack & Queue (concrete-first)

**No new Pass-2 node introduced here** — deliberate (see Method above). This milestone builds the *behavior* Barker's chain covers next (array list → stack → queue), using only Sequential representation (M2). The `Sequence ADT` node itself — the formal interface — is deferred to M5, once a second backing exists to formalize against.

- **Intuition:** Barker steps 4–5 (confirmed): stack as "a constrained array list — only touch the last element," queue as a circular buffer with a separate `start` index and modulo arithmetic, explicitly reusing the same modulo trick hashing will need later.
- **Friction problem:** given a working array list, implement undo/redo (Barker's own example) using only `insert-at-end`/`remove-from-end`. Notice these two operations are already O(1) on this representation — nothing new needs building, just a restricted way of using what exists. Then implement FIFO request processing the same way and notice the naive front-removal is O(n) — the queue's actual motivating problem.
- **Formalization:** name the restriction as a policy (LIFO / FIFO), not a new representation — stack and queue are "the same array list, a discipline layered on top." This is explicitly rehearsed again at M5 as "same interface, an added discipline, now over a second backing."
- **Implementation task:** circular-buffer queue over a fixed array (index wraparound via modulo).
- **Experiment:** none new — reuses M2's benchmarks.

**Checkpoint 1 project (after M3):** *A monitoring dashboard needs to keep the most recent N sensor readings from a continuous stream, discard the oldest one automatically the instant a new reading arrives once N is already held, report the newest reading in O(1), and never allocate more memory than N readings' worth, no matter how long the stream runs.* Restate the problem in your own words before choosing anything: what needs to be cheap, what's allowed to be expensive, what's the hard memory bound? (See the answer key at the end of this document for the intended solution and what it's testing — don't read it before attempting.)
- **Review checkpoint (per cross-cutting mechanisms), cumulative M0–M3:** (1) State, in one sentence, why `Operation cost as a function of representation` needed both Contiguity and Indirection "in view" before it could be motivated at all (M1). (2) Trace the amortized-cost argument for why doubling keeps dynamic-array append O(1) on average (M2). (3) Stack and queue are described in this curriculum as "the same array list, a discipline layered on top" — state precisely what discipline each one adds, without re-deriving new data structures.

## M4 — Recursion & Induction

**Nodes:** Recursive decomposition, Induction

**Why now:** `Self-referential structure` (next milestone) requires Recursive decomposition. Deliberately placed as its own milestone, ahead of any pointer-based structure, since Pass 2 split this out precisely because it applies equally to array-based algorithms — it shouldn't be introduced for the first time wearing a linked-list's clothing.

- **Formal:** Erickson's Recursion chapter (confirmed present, depth unverified, Pass 3); MIT 6.042 lectures 2–3 on Induction (confirmed, Pass 3) as the proof tool.
- **Gap #2, authored here (no clean mechanism explainer confirmed anywhere in the surveyed set):** the "unwind-the-box" model — a recursive call is a request to a *hypothetical, already-correct* solver for a strictly smaller instance, plus a small amount of glue work to turn that smaller answer into this one. The trust is provisional until the base case is reached and the calls unwind. Worked concretely on an array-based example that has nothing to do with pointers: computing the sum of an array via `sum(A, i) = A[i] + sum(A, i+1)`, base case `i == len(A)`. Trace it by hand on a 4-element array, writing out the actual call stack, before touching anything self-referential.
- **Friction problem:** write an iterative sum first (trivial), then write the recursive version and answer: what does the *call stack itself* look like right before the base case fires? This makes the "smaller instance" claim concrete rather than hand-wavy.
- **Formalization:** Induction, introduced immediately as the proof technique matching the pattern just traced (base case = base of induction, "trust the smaller call" = inductive hypothesis). State and prove correctness of the array-sum recursion formally.
- **Implementation task:** the array-sum recursion above, plus one more array-based recursive routine (e.g. reversing an array in place via two recursive index bounds) — deliberately choosing examples with zero pointers, to keep this node's independence from Indirection/Self-referential structure visible.
- **Experiment:** none — this milestone is proof-and-trace, not benchmarking.

## M5 — Indirection Made Structural: Linked Structures

**Nodes:** Self-referential structure, Linked (indirect) representation, Sequence ADT

**Why now:** Self-referential structure requires Recursive decomposition (M4) + Indirection (M1, already introduced as a bare concept). Linked representation requires Self-referential structure. Sequence ADT's linked-backed exemplar requires Linked representation — this is exactly the edge the verification script caught in an earlier draft (see Method).

- **Problem/friction:** CS 61B — IntList, confirmed and quotable ("IntLists are hard to use... must understand and utilize recursion even for simple list related tasks"), and unable to cleanly represent an empty list without scattered null-checks. Strongest confirmed friction narrative in the graph's early layers (Pass 1b/3).
- **Implementation:** CS 61B (SLList/DLList) for the on-ramp; ODS Ch. 3 (Linked Lists, Java) for the fuller interface+cost treatment once formalized (confirmed, Pass 3).
- **Intuition:** Barker (array's insert/delete cost → linked list, confirmed chain link).
- **Gap #9, authored here (linked-list "it's one array underneath" mechanism, dropped from Pass 3's carry-forward list but real):** before introducing a single language-level pointer or reference for this structure, build a linked list as next-*indices* inside a plain `int[]` — this is Barker's own construction (confirmed, transcript line 28: "each element stores the array index of the 'next' element... language-level pointers are themselves just indices into the array of memory managed by the heap allocator"). Two parallel arrays: `values[]` and `next[]`, where `next[i]` holds the index of the next node or a sentinel for "none." Insertion/removal only ever touches `next[]` entries, never shifts `values[]`. Only after this is working does the curriculum introduce `Node { value, next }` with a real reference — and the point to make explicit is that nothing changed mechanically, only the notation.
- **Friction problem:** IntList (CS 61B, confirmed) needs recursion for even the simplest list operations, and has no clean way to represent an empty list — trace through `insert`/`remove` on a one-element and a zero-element IntList by hand and name, precisely, what breaks or gets awkward in each case. Then design a fix for both problems before reading further.
- **Formalization:** CS 61B's actual fix, exactly as it does it (confirmed, Pass 1b): SLList wraps the recursive IntList structure in a non-recursive class (a `size` field and iterative traversal remove the "must recurse for everything" problem), and a **sentinel node** — a permanent, never-null placeholder node — eliminates the empty-list special case and the null-checks it forces. Two separate fixes for two separate problems named above, not one fix for both. Linked (indirect) representation as ODS's interface+cost treatment. Then retrofit `Sequence ADT`: the same push/pop/access interface from M3, now implementable over *either* backing — stated explicitly as "same interface, two answers," with a side-by-side cost table (array: O(1) amortized append, O(n) insert-at-front; linked: O(1) insert-at-front given a reference, O(n) indexed access). Access-pattern restrictions (stack/queue/deque) are re-stated as a policy layered on *either* backing, reusing the M3 vocabulary a second time rather than re-teaching it.
- **Implementation task:** the int-array-indices linked list (gap #9, above); then SLList/DLList with real references; then re-implement stack and queue over the linked backing and confirm the cost table's predictions against a benchmark.
- **Experiment:** CS:APP + JVM-boxing pairing #3 — this node *is* the reason `ArrayList<Integer>` breaks Barker's C-level cache-locality intuition in Java (per Pass 3): benchmark sequential traversal of an `int[]`-backed sequence vs. a real linked list of boxed nodes, and connect the gap to pointer-chasing + autoboxing specifically, not "linked lists are just slow."

## M6 — Disjoint-Set (Union-Find)

**Nodes:** Disjoint-set (union-find)

**Why now:** requires Self-referential structure + Operation cost as a function of representation, both satisfied by M5/M1. Deliberately pulled forward out of Pass 2's Layer 6 grouping (named decision #2, above) to serve as the curriculum's first complete worked instance of the friction-driven pattern.

- **Problem/friction:** Princeton's own three-act case study — confirmed, explicit, citable: quick-find (fast `connected`, slow `union` — O(n) per union) → quick-union (fast union, but trees can degenerate to a single long chain, making `find` O(n)) → weighted + path-compressed quick-union (near-constant amortized cost per operation). This is the README's own canonical example of "one interface, a sequence of implementations, each fixing the prior one's bottleneck" — teach it as exactly that, three explicit acts, not one final algorithm with two mentioned alternatives.
- **Implementation:** Princeton (algs4 code + booksite page, confirmed, Pass 3).
- **Visualization:** VisuAlgo's union-find page (confirmed present, Pass 1c).
- **Formalization, precise about what's derived vs. cited:** weighted union alone (no path compression) already gets a clean, derivable O(log n) depth bound, by an argument this curriculum can actually carry out: a node's depth only increases when its tree is merged into one *at least as large* (ties included — this is exactly the doubling case, not an edge case to wave away), and repeated doubling of the smaller side's size bounds the number of times any single node's depth can increase — the same doubling-bounds-the-damage counting shape as M2's dynamic-array argument, genuinely reused, not just gestured at. (**Precisely what's reused is the doubling-counting technique, not "amortization" as a label** — M2's O(1)-average-append claim is a genuine amortized bound spread across many operations; this O(log n) depth bound is a worst-case per-node structural bound proved by the same counting trick, not an amortized one. Don't conflate the two.) **Path compression's much stronger near-constant (inverse-Ackermann, O(α(n))) bound is a cited result here, not a derived one** — its actual proof needs machinery well beyond this doubling-counting argument, and asserting otherwise would overclaim what this milestone equips the learner to prove. State it as: "weighted union alone: O(log n) depth, provable now, by reusing M2's doubling-counting trick. Add path compression: O(α(n)) amortized, a real and citable result, left as a black box until a course with the room for it."
- **Implementation task:** all three acts, in order, each one benchmarked against the last on the same input (e.g. building a random spanning structure via repeated unions) to make the O(n) → O(log n) → near-O(1) progression a measured fact, not an asserted one.
- **Experiment:** compare quick-union's worst case (feed it an already-degenerate chain-shaped union sequence) against weighted union's same input — this is the moment "without balancing this degrades to a linked list" becomes visceral, which pays forward directly into BST-balancing at M10.

- **Comparison lower bound:**
  - **Gap #6, resolved this pass:** MIT 6.006 (Spring 2020), Lecture 5 "Linear Sorting" — notes fetched and text-extracted directly (`curl` + `pdftotext`), confirming the full decision-tree proof: binary decision tree, ≥n! leaves (one per output permutation), height Ω(log(n!)) = Ω(n log n) via the Stirling-style bound stated verbatim in the notes.   - Intuition: Barker, confirmed this pass (transcript line 29) — linear probing "walk forward to the next empty slot," clustering named as the downside. Corrects Pass 3's "Barker does not cover this at all," which conflated open addressing with chaining.
  - Formal: ODS Java §5.2 "LinearHashTable: Linear Probing," fetched and confirmed this pass — states and proves Theorem 5.2 (O(1) expected per operation, O(m) total amortized resize cost across m operations, via the same argument as the M2 `ArrayStack`). ## M14 — Algorithm Design Paradigms II: Dynamic Programming

**Nodes:** Overlapping subproblems, Memoization, Dynamic programming

**Why now:** Overlapping subproblems requires Recursive decomposition (M4). Memoization requires Overlapping subproblems + Contiguity (M1); its hash-keyed exemplar additionally requires Hashing (M9). Dynamic programming requires Memoization + Optimal substructure (M12).

- **Overlapping subproblems — formal:** MIT 6.006 L15, confirmed to open with "recursion, subproblems." Exemplar: naive recursive Fibonacci — standard intro example, covered by the same lecture.
- **Memoization — formal/implementation:** MIT 6.006 L15–L16. Exemplars: array-indexed cache (cross-link to Contiguity, M1); hash-keyed cache (cross-link to Hashing, M9).
- **Dynamic programming — formal:** MIT 6.006 L15–L18, the strongest, most granular citation in the whole document (confirmed — four full lecture parts; knapsack maps to the pseudopolynomial lecture, edit distance to the parens/piano-style string-DP lecture). Secondary, for breadth: K-T Ch. 6 + Erickson's DP chapter (both TOC-confirmed).
- **Friction problem:** trace naive recursive Fibonacci's call tree by hand at n=6 and count the *repeated* calls (e.g. `fib(2)` computed many times over) — this is Overlapping subproblems made visible, deliberately kept separate from any optimization claim (naive Fibonacci has no optimization objective at all, which is exactly the Pass-2 finding that split this node from Optimal substructure in the first place).
- **Formalization:** two explicit paradigm contrasts, both worth stating directly rather than leaving implicit:
  - **Greedy vs. DP** (both rest on Optimal substructure, M12): greedy commits to one locally-optimal choice per step, backed by an exchange argument; DP instead explores all choices and caches results, because overlapping subproblems make re-exploring wasteful.
  - **Divide & conquer vs. DP** (arguably the more fundamental contrast, per Pass 2 — about the *shape* of the recursion tree, not an optimization strategy choice): D&C's subproblems (M8's merge sort) are disjoint, so nothing is cached; DP's subproblems overlap, so memoization is the entire point.
- **Named callback, silent (decision #5, above):** memoization's cache-implementation choice — array-indexed vs. hash-keyed — is the contiguous/indirect fork's 5th occurrence. Unlike M11's graph-representation callback, this one is **not** named explicitly here. **Checkpoint 1 (after M3).** Intended solution: a fixed-capacity circular buffer of size N over a plain array, with a `start` index that wraps via modulo — M3's own queue construction, wearing different clothes (a "monitoring dashboard," not "implement a queue"). The point isn't that this is hard; it's whether the learner reaches for it *because* the constraints (bounded memory, oldest-out, newest-in-O(1)) forced it, rather than because the prompt said "queue." A learner who instead reaches for an unbounded list and manually deletes the oldest element on every insert has technically solved it but missed the O(1)/fixed-memory point — worth flagging as a partial pass, not a fail, and asking them to find the O(1) version.

**Checkpoint 2 (after M8).** This is Programming Pearls, Column 1 ("Cracking the Oyster") — confirmed as this project's problem-solving worked example back in Pass 1/Pass 3, placed here rather than left unassigned. Intended solution: a bit vector — one bit per possible value (0 through 9,999,999), initialized to zero; stream the input file once, setting bit k for every value k seen; then scan the bit vector in order from 0 upward, writing out every index whose bit is set. 10,000,000 bits is 1.25 MB decimal (1.19 MiB) — against a strict one-megabyte budget that's *over*, not under, so this alone doesn't close the problem; it's the realization that matters (presence-of-a-value needs exactly one bit, not a stored copy of the value — the same "the underlying array doesn't need to hold what you think it holds" move as M5's linked-list-as-indices task, and later M10's array-backed heap). The follow-up worth posing once the bit-vector idea lands: how would you fit this in a genuinely strict 1 MB? (A multi-pass approach — each pass covering only a fraction of the value range — shrinks the working bit-vector size per pass; Pearls' own text is understood to extend the problem in roughly this direction, though that specific extension wasn't independently fetched and confirmed this session, so treat it as a lead for the designer to verify, not a settled citation.) Read Pearls Col. 1 itself only *after* attempting this — it's the formalization step following the struggle, per the 1b learning-science condition this whole curriculum is built around, not a hint to read first.

**Checkpoint 3 (after M11).** The two sub-questions genuinely want two different tools, and noticing that is itself part of the answer — including noticing they are **not** equally cheap, which the prompt's "answer... fast" deliberately doesn't flag. "Are two accounts connected at all, across many repeated queries against a mostly-fixed link set" is M6's union-find — near-O(1) amortized per query once the structure is built, and it doesn't care about path length at all. "Fewest links between two accounts" needs actual shortest-path structure, which union-find deliberately throws away in exchange for that cheap query — this is BFS from M11, and a single BFS run costs O(V+E), which at tens of millions of accounts is not "fast" in the same sense union-find's query is. That asymmetry — cheap connectivity by discarding path information vs. expensive path-finding that requires keeping it — is the actual lesson, not a detail to smooth over: a learner who assumes both queries can be equally instant hasn't understood why union-find drops what it drops. Sparsity (links ≈ accounts, not accounts²) should independently push toward an adjacency-list-style representation over a matrix for the BFS half, though a learner who tries a matrix first and notices the memory blowing up has still found the right answer, just empirically instead of by prediction — that's fine.

**Checkpoint 4 (after M15).**
- **(a)** Order jobs by earliest due date ("EDD") — process the job with the earliest due date first among whatever remains, ties broken arbitrarily. This is optimal for minimizing maximum lateness on a single machine with no preemption and all jobs available at time zero. **This is not a fresh problem — it's Kleinberg-Tardos §4.2, "Scheduling to Minimize Lateness," the exact worked example this curriculum's own M12 reading already covers.** Confirmed this pass at the primary-source level, not just by search summary: Kevin Wayne's K-T lecture-slide PDF fetched directly and text-extracted via `pdftotext`, containing the section headings "Minimizing lateness: earliest deadline first," "Minimizing lateness: no idle time," and "Minimizing lateness: inversions" in sequence — the full proof structure (no optimal schedule has idle time; an "inversion" is a pair of adjacent jobs scheduled out of due-date order; swapping an inversion cannot increase the maximum lateness; repeat until no inversions remain). K-T's own definition of lateness there is exactly the floored one used in this prompt (ℓⱼ = max{0, fⱼ − dⱼ}), confirmed verbatim in the extracted text — an earlier draft of this checkpoint used an unfloored definition ("can be negative"), which didn't match the source it was claiming to recall and has been corrected. Recognizing the problem *as* that reading, and reproducing its exchange argument, is the actual test in (a) — not discovering something new. (The rule is also commonly attributed to Jackson, 1955, in the scheduling-theory literature generally; that attribution is stated from general recall, not independently verified by a fetch this pass, and is secondary to the K-T citation above, which was.)
- **(b)** A terminology caveat first, because it changes what a learner would find if they searched for this: the literature calls this floored, weighted, *summed* objective **total weighted tardiness**, not "weighted lateness" — "lateness" is conventionally reserved for the unfloored quantity, and K-T's slides only get away with calling the floored version "lateness" because their problem takes a max, not a sum, and for a max the floor genuinely doesn't change which schedule is optimal: max over jobs of max(0, lateness_j) equals max(0, max over jobs of lateness_j), so flooring each term before or after taking the max gives the same answer — a fact that stops holding the moment the floors are summed instead, which is exactly the (a) vs. (b) distinction here. Searching "weighted lateness minimization" turns up the *easy* problem, not this one, and here's why, checkable directly: the unfloored weighted objective Σ weight×(C_j − d_j) expands to (Σ weight×C_j) − (Σ weight×d_j), and the second term is a fixed constant, independent of scheduling order — so minimizing the unfloored version is *identical* to minimizing Σ weight×completion-time alone, which Smith's rule (sort by processing-time ÷ weight) solves via a clean exchange argument. **The floor is doing all the work of making this hard, not the sum.**
  With the floor back in (genuinely total weighted *tardiness* now), no single ordering rule survives, and the mechanism is a real reversal, not just a slowdown — worked concretely: job A (processing time 1, due date 1, weight 1) and job B (processing time 1, due date 2, weight 10), scheduled back-to-back. Starting at t=0: A-then-B costs 1×0 + 10×0 = 0 (both on time); B-then-A costs 10×0 + 1×1 = 1 — A first wins. Starting at t=10 instead: A finishing first or second, its lateness is 10 or 11 respectively; B's is 9 or 10. A-then-B: A finishes at 11 (lateness 10), B finishes at 12 (lateness 10) — cost 1×10 + 10×10 = 110. B-then-A: B finishes at 11 (lateness 9), A finishes at 12 (lateness 11) — cost 10×9 + 1×11 = 101. B-then-A wins. **The preferred order between these same two jobs flips depending on where in the schedule they sit.** Contrast this with EDD's unweighted max-lateness rule and with Smith's rule: in both of those, the *values* change with t, but the *preferred order* between any two specific jobs never reverses as t changes — which is exactly what lets one global sort work everywhere in the schedule. Here it does reverse, so no global sort can.
  Greedy failing doesn't mean nothing works — M14's own knapsack exemplar is exactly a case where greedy fails but DP still succeeds — so the honest next move, in this curriculum's own vocabulary, is to try a DP formulation before reaching for a hardness claim: let S be a set of jobs and P(S) the sum of their processing times (the completion time of whichever job finishes last among S, which — since a single machine's total elapsed time to process a fixed set of jobs doesn't depend on their order — is the same number no matter what order S was processed in); then f(S) = min over j in S of [f(S∖{j}) + weight_j × max(0, P(S) − due_j)] is a correct recurrence, computing the best way to schedule exactly the jobs in S. **But its state is a subset of jobs, not a bounded number** — unlike M14's knapsack, whose (item, capacity-used) state is *pseudo-polynomial*: polynomial in the numeric value of the capacity, not in the number of bits needed to write it down, which is exactly what "pseudo-polynomial" means and exactly why knapsack is only *weakly* NP-hard (a pseudo-polynomial algorithm is precisely the thing that can't exist for a *strongly* NP-hard problem unless P=NP). Here, which *specific* jobs are already done changes P(S) directly, with no numeric quantity to index by at all — so the state space is all 2ⁿ subsets, with no compression available even at knapsack's pseudo-polynomial level. (This is recall, not taught anywhere in this curriculum: total weighted tardiness is understood to be *strongly* NP-hard, unlike knapsack's weak hardness — consistent with there being no numeric index left to exploit, but not independently fetched and verified this pass, so flagged as recall like the hardness citation below.) That blow-up is evidence worth taking seriously, not proof — reaching it, and recognizing it as the kind of obstruction M15's vocabulary exists to name, is the real bar for (b). Single-machine total weighted tardiness minimization is, in fact, a known NP-hard scheduling problem in the general case (stated here from general scheduling-theory recall, not independently fetched and verified this pass, so flagged as such rather than cited as settled) — the DP blow-up above is a reason to suspect this, the citation is what would actually confirm it.
